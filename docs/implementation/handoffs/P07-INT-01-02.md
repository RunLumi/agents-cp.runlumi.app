# Work Packet Handoff — P07-INT-01/02

## What changed

The two **server-side seams** are complete. Neither has a LumiAgents-side change
in this repository, and this handoff says so plainly rather than implying a
round trip that was not performed.

### P07-INT-01 — plugin manifest/report

`POST /api/v1/orgs/{org_id}/plugin-reports` accepts what a host actually has
installed and answers with the policy verdict. The rule the gate states and the
code implements: **the server decides; the report is evidence, never authority.**
A report cannot approve anything. It can only downgrade an install to
`unreviewed` and record the verdict, so a host reporting a version the
organization never approved gets exactly that answer.

A report is refused — not partially accepted — when any entry declares a
destination the platform will not record (private, loopback, link-local, a
non-`http(s)/ws(s)` scheme, or a `*` pattern with no host in it). The refusal is
at the boundary on purpose: a declaration the platform refuses to record cannot
later be diffed, reviewed, or audited.

### P07-INT-02 — API/service identities

`require_machine` in `http/auth.rs` resolves a `MachineKey` into a `MachineActor`
and `GET /api/v1/machine/whoami` returns it. This is the path that lets a CI
pipeline or a managed runner call the control plane without borrowing a human
session cookie — which is the misattribution F14 exists to stop, because a
request made with a human cookie is attributed to that human in the audit trail.

Machine authority is an `ApiKeyScope`. There is no expression of it that becomes
a `MembershipRole`, and no conversion in either direction, so FR-F14-001's "MUST
NOT inherit an owner's permissions implicitly" is a compile-time fact rather than
a review rule.

## Runtime/deployment impact

- new bindings/env/secrets: none.
- Worker compatibility: unchanged.
- client-version assumptions: a reporting host must present a credential the
  org-scoped routes accept, because `/plugin-reports` is an **org-scoped customer
  route** gated on `plugins.manage`, not a machine route. A host reporting on its
  own initiative therefore needs an API key carrying `plugins.manage`.

## Known limitations

- **No LumiAgents repository was touched.** Both seams are server-side contracts
  that a host implements against. Until a host does, neither has been exercised
  by anything but this repository's own tests. This is the honest state of
  P07-INT-01/02 and it is why the Integration Gate is PASS WITH FOLLOW-UP rather
  than PASS.
- `/plugin-reports` is reachable by a human session with `plugins.manage` as
  well as by a machine key. That matches the gate's table, and it is worth
  knowing: a human reporting a host is reporting *about* a host, not *as* one.
- No impersonation route and no support console. F24-003's "default mode is
  metadata, not impersonation" is met by absence.

## Downstream agent notes

- A report entry is evidence. If you need to add a field that lets a report
  *approve* something, that is a gate change, not an implementation detail.
- `whoami` is the cheapest possible smoke test for INT-02: create a service
  account, mint a key, and call it. It proves the whole chain — parsing, hashing,
  lookup, scope, and the audit entry — in one request.

## Do not assume

- That a report can promote a review state. It cannot.
- That a machine can reach an org route that only calls `authorize`. It cannot:
  those handlers take `Option<&Principal>` and there is no conversion into one.
