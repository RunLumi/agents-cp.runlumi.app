## Tests added

**`apps/api/scripts/p07-schema-invariants.mjs` — 97 invariants, 0.26s, no
dependency.** The gate's central claim is that every security property is proven
*rejected by the database itself*, not merely asserted in Rust. An invariant
enforced only in application code is one code path away from being bypassed by a
migration, a script, or a future packet.

Four things the harness exists to prevent, three of which bit during probing:

1. **False positives.** A probe that violates a foreign key fails for the
   foreign key, not the trigger under test, and still reports "rejected". Every
   probe runs against a fixture known to be valid, and each case declares whether
   it expects accept or reject. There are 14 explicit `control:` cases.
2. **Order dependence.** Every case runs inside a rolled-back `SAVEPOINT`, so the
   suite is order-independent and idempotent — verified by running it twice.
3. **Fixture ordering.** The `0017`/`0018` cases were originally written to seed
   plugin rows before the user and organization they reference, and every probe
   failed on the foreign key. The seed is now one `db.exec` in dependency order.
4. **A single-trigger miss.** The terminal-state invariants are about what
   happens *after* a revoke, so they need a sequence. Probing one statement at a
   time reports "accepted" for a row that was never revoked — a passing test that
   proves nothing.

**Cross-tenant, in-database (5 new cases).** Isolation is a property of what a
scoped read returns, so the harness gained a `query` assertion alongside
`expect`. Each is written so that removing its `org_id` predicate makes it fail:
verified by deleting the predicates, which turns 97/97 into 94/97.

**Route and projection tests (31 new).** The three P07 route modules were the
only files in `routes/` with no test module. Notably `routes/internal.rs` has no
web client at all, so nothing on the other side would ever have caught a mistake
in its three projections.

## Known limitations

- **No P07 surface has been rendered in a browser.** No browser is attached to
  this session. Desktop and narrow layout, computed colours, real focus-ring
  appearance, and the async states of both sub-pages are visually unverified.
  This is the same debt P06 carries and it is the first thing a reviewer should
  check.
- **No end-to-end request against a running Worker.** The vertical slice below is
  proven at the domain, projection, and database layers and by `pnpm build`'s
  Worker dry run — not by an HTTP transcript. There is no local D1 with `0016`
  through `0018` applied and no recorded request IDs to cite.
- **No LumiAgents-side round trip.** Both INT seams are server-side contracts
  that no host has yet implemented.
- `docs/screens/` has no reference for any P07 surface. Only
  `lumi_rate_limits.webp`, `lumi_plan_entitlements.webp`, and
  `lumi_account.webp` were usable, as density and token references.

## Downstream agent notes

- `metadata.google.internal` is **not** refused as a network destination, and
  there is a test asserting that it is not. The check is on the host literal by
  design; a hostname blocklist is a policy decision the gate has not made. Do
  not read the passing test as a security claim.
- A support grant is created and revoked but **consumed by no route**. The grant
  is the frozen boundary a future support console must satisfy, and that is
  deliberate per the gate.

## Do not assume

- That a passing invariant is an enforcement mechanism. It proves the *database*
  refuses the write. Application-layer refusals are proven elsewhere.
- That 97/97 means the feature is safe. It means 97 declared behaviours match
  the DDL. The visual layer is unverified.
