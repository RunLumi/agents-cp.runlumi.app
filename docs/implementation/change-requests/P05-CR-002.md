# P05 Change Request — P05-CR-002

- Status: accepted
- Date: 2026-09-25
- Requested by: P05 coordinator
- Base contracts: `p05-cg-v1`, `p03-cg-v1`, `p04-cg-v1`
- Affected packets: P05-BE-01..04, P05-INT-01..04, P05-QA-01, and dependent FE decoders

## Reason for change

The first P05 contract freeze exposed integration gaps against the existing P03/P04 implementation: managed devices had no run lifecycle endpoints, approval/tool results were not consumable by the execution host, run correlation/version fields were incomplete, and the P03 compiler could not carry P05 budget/rate sections. Implementing those paths without an intentional clarification would create incompatible clients and unsafe accounting semantics.

This CR is additive and versioned. It does not change the F08/F12/F13/F16/F21 requirements or weaken P01/P02 authorization.

## P05-owned resolutions

### 1. Device run lifecycle API

Device-token routes are added under the existing P03 `/devices` namespace. The device's organization, project binding, active status, current membership, and current policy are resolved server-side; the body cannot select authority.

| Method | Path | Success |
|---|---|---|
| POST | `/api/v1/devices/sessions` | `201 Session` |
| POST | `/api/v1/devices/sessions/{agent_session_id}/runs` | `201 Run` |
| GET | `/api/v1/devices/runs/{run_id}` | `200 Run` |
| POST | `/api/v1/devices/runs/{run_id}/start` | `200 Run` |
| POST | `/api/v1/devices/runs/{run_id}/complete` | `200 Run` |
| POST | `/api/v1/devices/runs/{run_id}/fail` | `200 Run` |
| POST | `/api/v1/devices/runs/{run_id}/cancel` | `200 Run` |
| GET | `/api/v1/devices/runs/{run_id}/events` | `200 Page<RunEvent>` |
| POST | `/api/v1/devices/runs/{run_id}/tool-calls` | `201 ToolCallRef` |
| POST | `/api/v1/devices/runs/{run_id}/tool-calls/{tool_call_id}/result` | `200 ToolCallRef` |

Device mutations require `Idempotency-Key`; they do not use browser CSRF. The route derives `org_id`, `project_id`, `device_id`, `principal_user_id`, and policy context from the active device token and workspace binding.

### 2. Run projection/version/resume

The `runs` table/API projection adds:

```text
version                    optimistic projection version
state_version              increments on every valid state transition
workspace_binding_id       execution context used for the run
policy_snapshot_id         trusted snapshot used at start
policy_version             snapshot version used at start
cancel_requested_at        first cancellation request time
resumed_from_run_id        prior run when this is a resume, nullable
```

`version` and `state_version` are server-owned. RunEvent history remains append-only. `retry` uses `parent_run_id`; `resume` uses `resumed_from_run_id` and is a distinct endpoint/command. Resume re-evaluates current device, membership, project, model, tool, and budget policy.

The exact state edges are:

```text
queued -> dispatching | cancelled | failed | timed_out
 dispatching -> running | waiting_user | waiting_approval | cancelled | failed | timed_out
 running -> waiting_user | waiting_approval | succeeded | cancelled | failed | timed_out
 waiting_user -> running | cancelled | failed | timed_out
 waiting_approval -> running | cancelled | failed | timed_out
succeeded/failed/cancelled/timed_out -> no outgoing edges
```

`waiting_user` and `waiting_approval` are optional direct branches from dispatching/running; they are not mandatory sequential states. Repeated wait cycles are allowed only through a new validated transition and event.

### 3. RunEvent envelope and event names

Every RunEvent additionally carries `org_id`, `project_id`, `request_id`, `device_id`, `agent_session_id`, `schema_version`, and `recorded_at`. Actor semantics remain P01-compatible: device-originated events use `actor_type=system` with `device_id`; a user actor uses `user`. The event type set is extended with:

- `model.requested.v1`
- `model.response.v1`
- `tool.requested.v1`
- `tool.result.v1`
- `tool.decision_recorded.v1`
- `tool.denied.v1`
- `approval.requested.v1`
- `approval.resolved.v1`
- `error.occurred.v1`

Existing P04 `inference.*` and `usage.recorded.v1` events remain the canonical inference event names; P05 RunEvents reference their request IDs rather than duplicating payloads.

### 4. Approval binding and consumption

`ApprovalRequest` adds:

```text
agent_session_id
tool_fingerprint
arguments_hash
policy_snapshot_id
policy_version
requested_by_device_id
decision             approved | denied (set only on resolution)
consumed_at
consumed_by_device_id
```

A pending approval is bound to the exact tool ID, fingerprint, run/session, policy version, and SHA-256 hash of the bounded canonical argument summary. The device result endpoint atomically consumes a per-use approval before returning `allowed`; a second use returns `approval_already_resolved`/`approval_expired`. Session approvals still require current policy and exact scope at each use.

### 5. Tool policy rules and project scope

The P05 tool policy document adds typed `rules` entries:

```json
{
  "tool_id": "tool_0123456789abcdef0123456789abcdef",
  "capability_id": "cap_0123456789abcdef0123456789abcdef",
  "decision": "require_per_use_approval",
  "argument_scope": ["destination", "operation"]
}
```

Rules are evaluated after platform deny, project/org policy, agent constraints, and runtime capability. The API exposes organization policy and a project-scoped policy read/write under the same versioned document. A missing/malformed rule fails closed for privileged tools.

### 6. Internal accounting operations and dashboard reads

Client/browser APIs may create/update budgets and rate policies, but may not submit authoritative `reserved_minor`, actual cost, or reconciliation status. Reservation creation/reconciliation and usage ingestion are internal service-identity operations invoked by the inference/run engine. They are not public browser mutation routes.

Add read-only dashboard routes:

```text
GET /api/v1/orgs/{org_id}/usage/summary
GET /api/v1/orgs/{org_id}/usage/rollups
GET /api/v1/orgs/{org_id}/usage/denials
```

The first managed vertical slice keys reservations by the existing P04 `request_id` and correlates optional `run_id`; arbitrary client-selected reservation amounts are not accepted.

### 7. Usage source compatibility

P04 `usage_events` remains the immutable inference source and keeps its request-scoped foreign key. Non-inference run usage is stored in an additive `run_usage_events` source table with the same normalized usage/cost envelope and explicit `source='run'`; it is not a second reservation authority. Both sources feed the same read-only summary/rollup queries. A future migration may unify the physical tables after reconciliation evidence exists.

### 8. Audit correlation and retention

P05 adds nullable/indexed `run_id`, `agent_session_id`, and `tool_call_id` to security audit projections through a forward migration. New P05 data classifications are:

| Data | Owner/scope | Default retention/deletion |
|---|---|---|
| Agent/session/run metadata | org/project | organization retention policy; deletion request removes/anonymizes according to F20 |
| RunEvent/audit metadata | org/project | immutable security retention; no product delete |
| Tool arguments summary/hash | org/project/run | short bounded diagnostic retention; no raw arguments |
| Usage/CostRecord | org/project/principal | finance/audit retention; immutable |
| ArtifactRef | org/project/run | content lifecycle follows referenced content; metadata retained |
| Secrets/credentials | existing P04 scope | never in P05 tables/events/logs |

### 9. Dashboard/observability additions

P05 events and internal jobs carry `request_id`, `run_id`, `agent_session_id`, and bounded policy/route metadata. Metric labels use only service/route/result dimensions; IDs remain logs/events. Queue/job names and idempotency keys are stable per operation. P05-IG must report budget/rate denial, approval wait, reservation expiry, and reconciliation lag as evidence, without claiming unavailable platform signals.

## Coordinated P03/P04 compatibility clarifications

1. P05 coordinator owns a coordinated P03 policy compiler extension that accepts versioned `budgets` and `rate_limits` sections while preserving all existing P03 sections. P03 remains the only policy transport; P05 does not accept a client snapshot as authority.
2. P04 inference/request correlation continues to use `session_id` for the P02 login session. P05 uses `agent_session_id` everywhere for the F08 work Session.
3. P04 `usage_events` remains immutable and request-scoped. P05 `run_usage_events` is additive and must use the same cost/pricing/reconciliation rules.
4. P01 actor types remain unchanged; device-originated audit events use `system` plus `device_id`.
5. The local workerd passive-disconnect limitation remains explicitly conditional; no `request_cancelled` claim is permitted without an observed lifecycle row.

## Compatibility and migration

- Add the device routes, run projection columns, approval binding columns, run usage source, audit correlation columns, and dashboard reads in a forward P05 migration/contract patch.
- Do not edit already-applied P03/P04 migrations.
- P05 clients must tolerate absent optional P03 `budgets`/`rate_limits` sections by showing unavailable state; managed cloud work fails closed, local-only work remains distinguishable.
- Any further breaking change requires a new CR.

## Verification required

- Migration applies after `0009` on a fresh D1 database.
- Device start/complete/fail/cancel/tool-result flow is covered by hostile smoke.
- Cross-tenant, revoked-device, stale-policy, changed-argument, replayed-approval, and concurrent-budget cases fail closed.
- No public route accepts client authoritative cost/reservation values.
- Audit/run/usage correlation is queryable by request/run IDs.
