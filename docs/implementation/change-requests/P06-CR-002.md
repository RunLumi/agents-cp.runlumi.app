# Contract / Plan Change Request — P06-CR-002

## Trigger

F18 requires commercial plan, product entitlement, and upstream provider account state to remain distinct. The initial P06 draft exposed a browser entitlement-override route, used a single short license TTL for online freshness and offline grace, and did not define a provider entitlement projection. Existing P03 policy already has a singular `entitlements` extension and device policy authority, so adding a second `/devices/license` authority would create drift.

## Affected phase and packets

- Phase: P06
- Contract Gate: `p06-cg-v1` draft
- Active dependent packets: P06-MOD-02, P06-BE-03, P06-FE-03, P06-INT-02, P06-QA-01
- Merged dependent packets: none

## Proposed change

Current: Public browser overrides; one short-lived license snapshot; provider account state represented only as a future concern.

New: Overrides are internal/support-only with expiry, reason, scope, and F16 audit. Product logic consumes only stable Lumi entitlement keys. Existing `/devices/policy` carries the signed license block with separate `policy_fresh_until` and `offline_valid_until`. Provider coding-plan/account status is a separate read-only projection. Baseline grace is seven days for local-only, 24 hours for cloud control-plane operations, and no additional grace for platform-paid inference; capabilities may narrow these windows.

## Why this is necessary

This prevents payment-provider IDs, stale client flags, and an emergency support override from becoming product authorization. It also makes the local-first requirement explicit: a transient billing outage does not immediately brick unrelated local work, while paid cloud capabilities can fail sooner.

## Compatibility impact

- API: no public override route; add provider entitlement read and billing portal/session reads/mutations.
- schema: additive billing account, provider projection, plan entitlement, subscription event, grant, and license metadata tables.
- FE fixtures/types: show Lumi subscription, provider account state, grace, and remediation separately.
- LumiAgents protocol: verify the signed block in the existing P03 policy response; no second license endpoint.
- migrations: additive `0012`/`0013` sequence; no P03 migration rewrite.
- security: provider references and signing keys remain server-only; overrides require audited service identity.
- existing data: current `entitlements` schema-0 snapshots remain valid only as legacy placeholders and are upgraded by the P06 compiler.

## Alternatives considered

1. Let admins create permanent overrides in the browser; rejected because F18 requires expiry/reason/audit and support-only authority.
2. Keep a separate `/devices/license` endpoint; rejected because it would become a second policy authority.
3. Treat provider coding-plan loss as Lumi subscription cancellation; rejected by F18.
