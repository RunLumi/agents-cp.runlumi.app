# Contract / Plan Change Request — P02-CR-002

## Trigger

P02 shipped a secure email one-time-code authentication slice, but the product requirement has changed: **passkeys must be the first/default registration and login option, while email + password must be the second/fallback option**.

The current frozen P02 contract and UI do not express that hierarchy. Passkeys were explicitly left out of P02-BE-02, and the existing web screen presents email one-time-code as the only normal sign-in path.

## Affected phase and packets

- Phase: P02, already complete
- Current Contract Gate: `p02-cg-v1` at `ba35fb6`, clarified by P02-CR-001 at `0290e68`
- New contract version after this amendment: `p02-cg-v2`
- Merged historical packets remain immutable
- New additive packets:
  - P02-MOD-05 — authenticator credential domain
  - P02-BE-05 — passkey/password persistence and auth APIs
  - P02-FE-04 — passkey-first authentication UX
  - P02-QA-02 — passkey/password hostile and compatibility matrix
- P03/P04 remain unblocked because principal/session/org contracts do not change.

## Proposed change

### Authentication priority

Normal registration and login UX MUST be ordered:

1. **Passkey** — primary/default option.
2. **Email + password** — secondary/fallback option.
3. Existing email one-time-code flow remains only for email verification, recovery, backwards compatibility during migration, and other explicitly scoped challenge flows. It is not the normal primary login CTA after P02-CR-002 is implemented.

### Passkey registration

Passkey signup is a two-step server-authoritative WebAuthn ceremony.

The server starts a short-lived, one-time registration ceremony using an opaque pending user handle and explicit configured RP ID/origin policy. The browser creates a discoverable credential. Only after successful server verification may the backend atomically create/link the user, email identity, passkey credential, session, and security event.

Defaults:

- discoverable credential required so login can be usernameless;
- user verification required;
- attestation `none` unless a later enterprise policy requires attestation;
- do not force `authenticatorAttachment=platform`; allow synced passkeys and security keys;
- email remains required as contact/recovery identity and must still be verified before email-sensitive org flows such as accepting an invitation.

### Passkey login

Passkey login MUST support discoverable/usernameless authentication. The start endpoint MUST NOT require email and SHOULD omit `allowCredentials` for normal passkey login.

The web login page SHOULD also use conditional mediation/autofill when the browser supports it, while retaining an explicit “Sign in with passkey” primary button.

Authentication maps the verified credential ID/user handle to the account. The client never chooses the authenticated `user_id`.

### Password fallback

Email/password is the second option, not the default CTA.

Passwords MUST:

- be hashed, never encrypted or directly SHA-hashed;
- use Argon2id at or above the current OWASP baseline when that can be safely supported in the Cloudflare Worker WASM runtime;
- be benchmarked under the real Worker/WASM memory and CPU limits before rollout;
- use a compatibility/architecture decision rather than silently weakening the KDF if the required parameters are not viable;
- support long passwords (at least 64 characters maximum), password managers/paste, and no arbitrary composition-rule theatre;
- use generic login/reset responses where account enumeration matters;
- be independently rate limited.

### Recovery and authenticator management

Users may register multiple passkeys and label/revoke them.

A user MUST NOT be allowed to remove the last usable sign-in method unless another usable passkey or password recovery/sign-in method exists.

Verified email is the recovery anchor for lost-passkey/password-reset flows. Recovery, password reset, passkey add/remove, and suspicious authenticator events are auditable security events.

## API amendment

Additive P02 v2 routes:

| Method | Path | Context | Purpose |
|---|---|---|---|
| POST | `/api/v1/auth/passkey/signup/start` | anonymous | Begin passkey-first account registration |
| POST | `/api/v1/auth/passkey/signup/complete` | anonymous ceremony | Verify credential, create account/session |
| POST | `/api/v1/auth/passkey/login/start` | anonymous | Begin discoverable/usernameless assertion |
| POST | `/api/v1/auth/passkey/login/complete` | anonymous ceremony | Verify assertion, create session |
| POST | `/api/v1/auth/password/signup` | anonymous | Secondary email/password registration |
| POST | `/api/v1/auth/password/login` | anonymous | Secondary password login |
| POST | `/api/v1/auth/password/forgot` | anonymous | Generic password recovery start |
| POST | `/api/v1/auth/password/reset` | recovery challenge | Reset password and apply session policy |
| GET | `/api/v1/account/passkeys` | session | List passkey metadata |
| POST | `/api/v1/account/passkeys/register/start` | session + recent reauth | Begin additional passkey registration |
| POST | `/api/v1/account/passkeys/register/complete` | session + ceremony | Add passkey |
| DELETE | `/api/v1/account/passkeys/:passkey_id` | session + recent reauth | Revoke passkey |
| POST | `/api/v1/account/password` | session + recent reauth | Set/change fallback password |

Existing `/auth/signup`, `/auth/login/start`, and `/auth/login/complete` remain temporarily compatible with the shipped email-challenge flow until a deliberate deprecation/removal step. The post-CR-002 web UI does not present them as the primary normal login path.

## Persistence amendment

Additive schema will require, at minimum:

- `passkey_credentials`: credential ID, user, public key, sign counter/metadata, backup flags where available, transports, label, created/last-used/revoked timestamps.
- `webauthn_ceremonies`: one-time short-lived server-side ceremony state, kind, challenge/state, expected policy, pending user/email metadata as needed.
- `password_credentials`: one current password hash per user plus algorithm/work-factor metadata and timestamps.
- recovery challenge/state using the existing challenge model where safe or a narrowly scoped additive table if required.

No private key or raw password is ever stored.

## Web UX amendment

On both sign-up and sign-in:

- Passkey is visually first and receives the primary CTA.
- A clear “or” separator precedes email/password.
- Password UI is secondary but fully accessible.
- On supported browsers, login may offer passkey autofill/conditional mediation with `autocomplete="username webauthn"`.
- If passkeys are unavailable in the current browser/context, password remains usable without a dead-end.
- Email one-time-code UI is reserved for verification/recovery/compatibility, not the main sign-in panel.

## Security invariants

Passkey verification MUST validate server-generated one-time challenge, RP ID, expected origin, credential public key/signature, and required user verification.

WebAuthn ceremony state is server-side, short-lived, one-time, bounded, and rate limited.

Do not implement WebAuthn cryptographic verification ad hoc. Use a maintained verifier only after proving it works under `wasm32-unknown-unknown` and the Worker runtime.

A zero/non-incrementing signature counter MUST NOT by itself reject synced passkeys. A meaningful positive-counter regression may create a security event/step-up according to verifier guidance.

## Why this is necessary

Passkeys provide phishing-resistant public-key authentication and are now a mainstream browser/platform capability. Making them the primary path materially reduces password exposure while preserving a familiar fallback for users/devices that cannot use passkeys.

The repository's current custom Rust/Cloudflare auth stack also means the change must be explicit about WASM compatibility and ceremony state. Treating “WebAuthn-ready” as equivalent to a secure implementation would be a dangerous shortcut.

## Compatibility impact

- API: additive; existing P02 session/cookie/CSRF/principal contracts remain stable.
- Schema: additive migrations only.
- FE: auth screen hierarchy changes; existing org/account flows remain compatible.
- LumiAgents desktop: browser-based handoff remains compatible. A user can authenticate in the browser with passkey or password before approving the existing PKCE device flow.
- P03/P04: remain ready/unblocked.
- Security: stronger default authentication path; new credential/recovery surface requires its own hostile matrix.

## Alternatives considered

1. Keep email OTP as primary and merely add a “passkey” settings page — rejected because it does not satisfy passkey-first registration/login.
2. Replace the entire P02 auth stack with an external auth SaaS immediately — rejected as an unvalidated architecture change.
3. Implement WebAuthn signature verification manually — rejected because authentication crypto should use a maintained verifier with tested WebAuthn semantics.
4. Store passwords with a fast hash because Workers are resource-constrained — rejected; runtime constraints must be measured and resolved explicitly, not by weakening credential storage.

## Decision

- accepted

Decision rationale: passkey-first + password-fallback is the new product requirement. The change is additive to the shipped P02 principal/session model and should be implemented as a focused auth upgrade rather than reopening unrelated tenant functionality.
