# Contract / Plan Change Request — P03-CR-001

## Trigger

Implementing P03-BE surfaced three concrete cases the frozen P03-CG does not
name, each of which needs a stable `error.details.reason` or a storage home:

1. Enrollment approval of a device whose key fingerprint already exists in the
   org needs a distinct denial reason from generic `conflict` (the retry
   semantics differ: re-enrolling the same physical key is a user error, not a
   transport retry).
2. `POST /orgs/{org_id}/projects` with an already-taken slug needs
   `project_slug_conflict` for the same reason.
3. Minimum-client-version enforcement (F19-008, plan03 P03-BE-03) needs a
   durable per-org setting; the CG defined the check but no storage home.

## Affected phase and packets

- Phase: P03
- Contract Gate: `p03-cg-v1` (merged as PR #9, `7952bd7`)
- Active dependent packets: P03-MOD-01..03, P03-BE-01..03 (not yet merged)
- Merged dependent packets: none

## Proposed change

Current: denial-reason registry ends at `device_not_approved`; no org-level
min-version setting storage.

New:

- Append `device_fingerprint_conflict` and `project_slug_conflict` to the
  stable denial/lifecycle reason registry.
- Add `org_device_policy_settings` table (PK `org_id`, nullable
  `min_client_version`, `updated_at`) to migration `0007`.

New (same as above); API/error envelope shapes unchanged.

## Why this is necessary

Use facts from implementation: duplicate-key enrollment and duplicate slug are
distinct user errors that clients must branch on differently from transport
retries; without a settings row, the F19-008 check in the device token
exchange has no authoritative input. Generic `conflict` would force clients to
parse messages, violating F23.

## Compatibility impact

- API: additive reason strings only; envelope unchanged.
- schema: additive table + two appended reason strings.
- FE fixtures/types: none yet consumed.
- LumiAgents protocol: none yet consumed.
- migrations: 0007 is amended before first application anywhere; no applied
  environment is affected.
- security: no change (reasons are non-secret classifications).
- existing data: none.

## Alternatives considered

1. Reuse generic `conflict` without a reason — clients would parse English
   messages, violating F23.
2. Ship min-version enforcement without storage — the check would be dead
   code and F19-008 unverifiable.
